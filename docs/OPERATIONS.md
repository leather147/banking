# Операции и локальное состояние

## Модель

`OperationRecord` выводится из `operationSchema` и является единым форматом для перевода, пополнения и платежа.

Ключевые поля:

| Поле | Назначение |
| --- | --- |
| `slug` | уникальный адресуемый идентификатор |
| `kind` | `transfer`, `top-up` или `payment` |
| `status` | `completed`, `processing` или `failed` |
| `amount`, `fee`, `currency` | денежное представление операции |
| `source`, `recipient` | уже маскированные display-значения |
| `rejectionReason` | обязательный для содержательного failed UI |
| `scheduledAt` | отложенное исполнение |
| `details` | дополнительные строки квитанции |
| `legalReference` | ссылка на применимый раздел демо-правил |

Форма может иметь собственные промежуточные поля, но перед сохранением обязана нормализовать их в эту модель.

## Slug и маршруты

Slug состоит из типа, времени в base36 и короткого случайного фрагмента. Он не является секретом и не используется как доказательство авторизации.

```text
transfer-msgrimgt-327d85a
└─ kind └─ time └─ random
```

- `createOperationPath` создаёт адрес формы конкретной операции;
- `operationDetailsPath` создаёт адрес итоговой квитанции;
- route сохраняется в истории браузера и работает при прямом reload.

## Хранение

Cookie имеют типичный лимит около 4 KB, поэтому история разделена:

- `lumen-operation-index` содержит не более 24 slug;
- `lumen-operation-<slug>` содержит одну нормализованную операцию.

При чтении индекс проходит Zod-проверку, каждая операция проверяется отдельно, а повреждённая запись пропускается. Встроенные fixtures добавляются после пользовательских операций и не дублируются по slug.

Это решение подходит только для прототипа. Реальный сервис обязан хранить операции на сервере, отдавать их авторизованному пользователю и использовать idempotency key при создании.

## Сценарий создания

1. `OperationStartButton` создаёт slug и делает client navigation.
2. Экран определяет активный scenario по route kind.
3. Маски ограничивают форму допустимым визуальным форматом.
4. Zod проверяет данные перед review.
5. `ReviewDialog` показывает сумму, комиссию, источник и получателя.
6. Desktop подтверждает кнопкой, touch/mobile — swipe-контролом.
7. `saveOperation` записывает нормализованную сущность.
8. Router открывает `/operations/[slug]`.

## Swipe-confirm

Контрол использует pointer capture, поэтому drag не теряется за границами thumb. Текущий progress дублируется в ref: `pointermove` и `pointerup` могут попасть в один React batch, а подтверждение должно использовать последнее физическое положение указателя, не предыдущее render-state.

Порог подтверждения — 88%. Клавиатура меняет значение стрелками и подтверждает Enter/Space после достижения порога.

## Статусы

- `completed` — акцентное успешное оформление и доступный чек;
- `processing` — нейтральное серое оформление, отсутствие ложного обещания исполнения;
- `failed` — красный статус и конкретная причина отклонения.

Статус не следует выводить только цветом: рядом всегда присутствует текст и иконка.

## Чек и share

Скачиваемый `.txt` содержит только display-данные текущей операции и предупреждение о демонстрационном происхождении. Progress управляется таймером и закрывается вместе с экраном, чтобы toast не оставался после navigation.

Share dialog передаёт короткую сводку: статус, заголовок, сумму и slug. Полный номер карты, телефона, счёта и документы пользователя не включаются. Внешние сервисы открываются с `noopener,noreferrer`.

## Добавление нового типа операции

1. расширьте `operationKindSchema`;
2. добавьте route mapping и transaction category;
3. создайте стартовый и итоговый маршрут;
4. добавьте форму и Zod schema;
5. определите receipt details и legal reference;
6. обновите историю, поиск и i18n;
7. проверьте completed/processing/failed и reload прямого URL.
